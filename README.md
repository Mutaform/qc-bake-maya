# QC Bake for Maya

QC Bake is a Maya tool by Mutaform Studio for preparing high-poly and low-poly
object name pairs for texture baking workflows.

Select the meshes for an asset and press **Create Namepair**. QC Bake works out
which object is the high poly and which is the low (by triangle, face or vertex
count) and renames them into a matching pair using the suffixes of the chosen
naming convention. Multiple high polys, an optional cage, outliner organisation
and role-wide visibility are all supported.

This is a port of the QC Bake Blender extension and carries the same feature
set as its 2.0.0 release.

## Compatibility

- Maya 2025 (Python 3.11, PySide6)

## Install

1. Download `qc_bake_maya-<version>.zip`.
2. Unzip it **where it can stay** - a tools folder, a network share, anywhere
   permanent. See the note below.
3. Drag `install/install.py` from the unzipped folder into a Maya viewport.

That is the whole install. It writes a Maya module file pointing at the folder
you unzipped, adds a **QC Bake** button to a *Mutaform* shelf, and opens the
panel. Maya picks it up on every launch from then on.

**The unzipped folder is the installation.** Nothing is copied into Maya's own
directories - the module file is a pointer, which is what makes an update a
matter of replacing that folder and nothing else. The flip side is that moving
or deleting it breaks the tool; if that happens, unzip again and drag
`install.py` in once more.

`tests/test_install_maya.py` rehearses exactly these steps from the published
archive, so the instructions above are checked rather than remembered.

From the script editor instead:

```python
import sys
sys.path.insert(0, r"C:\path\to\qc-bake-maya\install")
import install
install.install()
```

To remove it, `install.uninstall()`. The repository itself is left alone.

## Releases

`tools/build_release.ps1` writes three things from one run:

- `dist/` - wiped and rebuilt each time;
- `Zip Addon/` - the studio's local store of built releases, named
  `qc_bake_maya-<version>.zip`. Never cleared by a build, so an artist can be
  handed the exact version they were running. Not committed: it lives beside
  the repository, not inside it;
- `pages/` - the zip plus the `version.json` that drives updates, which the
  workflow publishes to `gh-pages`.

All three come from the same build, which is what stops the manifest ever
describing an archive it did not produce.

## Updates

Maya has no add-on repository. A `.mod` file is a path pointer and nothing
more, `moduleInfo` knows nothing about versions, and the only official channel
with update notifications is the Autodesk App Store - a `.bundle`, a review
queue, and a notification rather than an install. So the update mechanism is
ours.

QC Bake asks a manifest published on GitHub Pages whether a newer release
exists, and if there is one it says so at the top of the panel. It never
installs on its own. Pressing **Install** downloads the archive, checks it
against the digest the manifest declares, unpacks it, swaps it into place and
reloads the package without restarting Maya - and keeps the previous version
until the new one has actually imported, so a broken release puts itself back.

The check runs in a background thread at most once every six hours, so a
studio proxy that swallows the request can never stall Maya, and a failed
check stays quiet unless you asked for it. Turn it off, or run it on demand,
under **Options > Updates**.

Publishing a release is `tools/build_release.ps1`, which writes `pages/` with
the zip, `version.json` and an index page; `.github/workflows/pages.yml` does
the same on every push to `main` and publishes to `gh-pages`. The manifest is
generated by the build rather than written by hand, because a manifest whose
version disagrees with the archive beside it advertises an update that
installs nothing and is then offered forever.

## The shelf icon

`qc_bake_maya/resources/qc_bake_32.png` - the flame, drawn as flat vector in
three layers. It lives inside the package rather than beside it so that it
travels: into the release archive, and through an update, which swaps the
package folder and nothing else.

`icons_src/` holds the source: `flame.py` has the shapes, `make_icon.py`
renders the PNGs into the package (it needs Qt, so run it inside Maya). A
shelf button draws at 32x32, which is the whole design constraint; the 64 and
128 files are there for high-DPI displays. After regenerating,
`install.refresh_shelf_icon()` re-applies it without a reinstall.

## Using it

**Create Namepair** takes the selection and renames it. With two meshes
selected, the denser one becomes the high. With three or more, one is the low
and the rest become indexed highs (`asset_high_01`, `asset_high_02`); the low is
the last mesh you selected if *Track Selection Order* is on, and the smallest
mesh otherwise.

**Swap High / Low** flips the roles of a pair when the automatic choice picked
wrong - a dense low poly against a sparse blockout, for instance.

**Visibility** shows or hides whole roles at once. It works through display
layers, so it never overwrites the visibility state you set by hand: switching
a role back on restores what was there rather than what QC Bake guessed.

**Reduce Bake Groups** merges namepairs that sit far enough apart into fewer
bake groups, so several assets can share one texture set. Two assets may only
share a group when their world bounding boxes stay at least *Minimum Gap* apart,
which is what stops rays cast from one asset striking another one's high poly.
Every rename is backed up into the scene file, so **Restore** still works
tomorrow - long after Maya's undo queue has been emptied.

**Collection Layout** reorganises the outliner: *Flat* groups by role
(High / Low / Cage), *Per Asset* gives each namepair its own `Bake_<name>`
group, tinted green when the pair is complete and red when a member is missing.
Both layouts live under one `Bake_Group` head, and membership is decided purely
by name suffix - props and helper meshes are never touched. Grouping does not
move geometry.

## What is different from the Blender version

Everything the Blender add-on does, this does. Five things behave differently
because Maya does, and each is a deliberate decision rather than an accident:

| | Blender | Maya |
|---|---|---|
| Settings live | in the .blend | in optionVars, so a convention follows the artist rather than the file |
| Containers | collections | groups, with display layers doing the show/hide |
| Show / hide | per-object | display-layer overrides, which leave `.visibility` untouched |
| Name clashes | abort, or auto-`.001` | abort, or let Maya auto-number to `name1` |
| Smooth preview | subdivision modifiers counted | invisible to `polyEvaluate`, so *Count Smooth Preview* folds it back in |

Maya also has namespaces and per-parent name uniqueness, neither of which exists
in Blender. Renames keep a referenced object inside its namespace, and every
lookup travels as a full DAG path so that two `asset_low` nodes in different
groups are still reported as the clash they are.

## Layout

```text
qc_bake_maya/
  __init__.py      version, and the show() entry point
  core.py          pure logic - no Maya import, so it is testable anywhere
  naming.py        DAG paths, namespaces, Maya name validation
  scene.py         the only module that talks to maya.cmds
  prefs.py         settings, stored in optionVars
  icons.py         every icon the UI uses, in one place
  commands/        one module per action
  ui/              the dockable PySide6 panel
  resources/       the shelf icon, shipped with the package
install/
  install.py       drag-and-drop installer
icons_src/         icon artwork and its generator
tools/
  build_release.ps1
tests/
  test_core.py         logic tests - plain python, no Maya needed
  test_scene_maya.py   integration tests - run inside Maya
  test_updater.py      updater tests - plain python, no Maya needed
  test_panel_maya.py   panel tests - run inside Maya
  test_install_maya.py first-install rehearsal - run inside Maya
```

## Tests

The logic layer imports nothing from Maya, so it runs anywhere:

```bash
python tests/test_core.py
python tests/test_updater.py
```

The integration tests need a running Maya and are destructive to the open
scene - they call `file -new` repeatedly and save nothing:

```python
import sys
sys.path.insert(0, r"C:\path\to\qc-bake-maya")
import importlib.util
spec = importlib.util.spec_from_file_location(
    "qcbake_tests",
    r"C:\path\to\qc-bake-maya\tests\test_scene_maya.py")
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)
module.run()
```

`tests/test_panel_maya.py` runs the same way and covers the panel itself. Its
`run()` holds everything decidable in one go; proving that a scriptJob really
fires needs Maya's event loop, which a script never reaches, so that check is
split into `setup_deferred()` / `fired()` / `finish_deferred()` for the caller
to poll between idle moments.
